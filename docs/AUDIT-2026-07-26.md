## 1. Executive summary

HomeApp is in noticeably better shape than the open issue list suggests. The commits from 2026-07-25/26 (`e1645fe`, `3af20b9`, `9f1692c`, `2ea0b19`) genuinely closed a cluster of real problems: soft-delete now survives a sync, the repository is local-first, reminders are per-user and cancel correctly, snooze works, the `u1`/`u2` literals are gone from the data path, RLS no longer 403s on the revision trigger, and scheduled notes are hidden server-side by an RLS predicate. Eleven of the original P0/P1 issues were closed on merit, not by hand-waving. The architecture is small, readable and appropriate for its job: ~2,600 lines of Kotlin, no DI framework, no Room, no ViewModel layer — a single `HomeRepository` owning `StateFlow`s, a SQLite payload cache, and PostgREST over OkHttp.

What the issue list *doesn't* capture is that the most valuable recent change is not actually reachable by the user, and that the write path has concurrency holes of exactly the kind that produced the last round of "my change disappeared" bugs.

**The five things that matter most:**

1. **The local-first repository is walled off behind an online-only UI.** `HomeRepository.save()` (`HomeRepository.kt:188-213`) never needs the network — it writes SQLite first and pushes in the background. But the Add sheet's save button is `enabled = online && canSave` and reads *"cannot edit while offline"* (`QuickAddScreen.kt:151-152`), and pin / archive / delete / complete / set-reminder in the detail screen are all gated on `online` (`DetailAndSettingsScreens.kt:86, 87, 157, 213`). Meanwhile comments, checklist toggles and title/body edits on the *same screen* are **not** gated. So the app is both offline-hostile and inconsistent about it. Deleting five `online &&` guards converts v1.1.0's local-first work into a feature. This is the single highest value-per-line change available.

2. **The pending-push set is an unsynchronized read-modify-write, and `save()` doesn't hold the sync lock.** `markPending`/`clearPending` do get→modify→set on one comma-joined metadata string with no mutex (`HomeRepository.kt:142-145`); two concurrent saves lose one flag. Worse, `save()` never acquires `syncMutex`, so `syncNow()`'s `database.replaceAll(merged)` (`HomeRepository.kt:174`) can run between a save's `database.upsert` (`:202`) and its `markPending` (`:203`) and delete the brand-new row from SQLite — after which `pushPending()` finds no local copy and *clears the pending flag* (`:152`). The item stays in the in-memory list until the next app start and then is simply gone. Since every local write echoes back over Realtime and triggers a full `syncNow()`, this window is opened by normal use, not by a stress test. This is the same failure *class* the last release fixed, one layer down.

3. **Two switches in the UI do nothing.** "הודע למשתמש השני" (notify the other user) sets `notifyOtherUser` (`QuickAddScreen.kt:118, 147`), which is encoded, decoded, and never read by anything. "תוכן במסך נעילה: גלוי/מוסתר" writes `lockScreenContentVisible` (`DetailAndSettingsScreens.kt:404-405`), which is never read either — `ReminderReceiver` sets no `setVisibility()`. For a two-person app these are the two settings most likely to be *trusted*, and one of them is a privacy control.

4. **Household separation leaks across a logout.** `logout()` calls `database.clearAll()` (`HomeRepository.kt:294`), which only deletes from the `items` table (`LocalDatabase.kt:35`). The `metadata` table survives, so preferences, `pending_push` and — importantly — `notifications_seen_at` carry over to whoever activates next; their notifications arrive pre-marked as read. The PIN (`PinVault`) and the alarm registry (`ReminderScheduler.kt:15`) are not cleared either, and previously-set alarms are never cancelled, so the departing member's reminders keep firing on the device.

5. **The safety net is thinner than it looks.** There are 13 unit tests in 3 files; **2 of the 3 tested units (`ConflictResolver`, `RecurrenceEngine`) are dead code with no production call site**, so the tests protect nothing that ships. There is zero coverage of `JsonCodec`, `LocalDatabase`, `HomeRepository`, sync merge, or the pending-push set — i.e. every component implicated in findings 2 and 4. CI runs only `test assembleDebug` (`android.yml:27`) even though `lint { abortOnError = true }` and a minified release build are both configured (`build.gradle.kts:42-52`) and never exercised.

**Overall verdict:** this is a healthy small codebase with a good recent trajectory. It is *not* at risk of catastrophic failure, but it has a narrow class of silent data-loss windows in the write path that will keep producing "it vanished" reports until the write path is serialized. Fix items 1, 2 and 3 and the app becomes materially more trustworthy for about a day's work.

## 3. New findings not covered by the issues

Severity: **P0** = silent data loss or security; **P1** = user-visible wrongness or a maintenance trap; **P2** = quality/robustness.

### N1 — [P0] The UI blocks offline writes that the repository fully supports, and does so inconsistently

**What's wrong.** `HomeRepository.save()` (`HomeRepository.kt:188-213`) writes to SQLite, updates the in-memory flow and marks the item pending *before* it ever touches the network; the push at `:205-209` is best-effort and a failure is explicitly tolerated. Nothing in the write path requires connectivity. Yet:

- `QuickAddScreen.kt:151-152` — `enabled = online && canSave`, with the label `if (online) "שמירה" else "לא ניתן לערוך במצב לא מקוון"`. You cannot create *anything* offline.
- `DetailAndSettingsScreens.kt:86` (pin), `:87` (the overflow menu holding archive + delete), `:157` (the whole reminder card is hidden), `:213` (mark-complete) — all gated on `online`.
- But `:119-126` (save title/body/assignee/date), `:173` (checklist toggle), `:180` (add checklist entry), `:210` (post a comment) are **not** gated.

`online` comes from `ConnectivityObserver`, which requires `NET_CAPABILITY_VALIDATED` (`ConnectivityObserver.kt:17`) — a captive-portal or flaky-Wi-Fi state reports offline even when the phone has signal.

**Why it matters to this couple.** The two most common real-world moments for this app are the supermarket and the car — exactly where connectivity is worst. Today: you can tick a checklist item at the supermarket but cannot add one from the Add sheet; you can comment on an event but cannot mark the task done. The inconsistency is worse than a uniform block, because it teaches distrust of the whole app.

**Fix.** Delete the five `online &&` / `&& online` guards listed above and the offline label. Keep `OfflineBanner` (`HomeAppRoot.kt:238`) and add a small per-item "pending" indicator sourced from `pendingIds()`. Effort **S**. App-code only. This should be done together with **N2/N3**, since it increases offline write volume.

### N2 — [P0] `pending_push` is an unsynchronized read-modify-write; concurrent saves silently drop sync flags

**What's wrong.**

```kotlin
// HomeRepository.kt:142-145
private fun pendingIds(): Set<String> =
    database.getMetadata("pending_push")?.split(",")?.filter { it.isNotBlank() }?.toSet() ?: emptySet()
private fun markPending(id: String) = database.setMetadata("pending_push", (pendingIds() + id).joinToString(","))
private fun clearPending(id: String) = database.setMetadata("pending_push", (pendingIds() - id).joinToString(","))
```

Read → modify → write over a single delimited string, with no mutex, invoked from `save()` on `Dispatchers.IO` (`:203, 207, 209`) and from `pushPending()` (`:154`) concurrently. Classic interleaving: save(A) reads `{}`, save(B) reads `{}`, save(A) writes `{A}`, save(B) writes `{B}` — A's pending flag is gone. If A's own push also failed (offline, expired session, server hiccup) A is now a local-only edit that **no retry will ever pick up**.

The set also grows unboundedly as a single comma-joined string in one SQLite cell; there is no cap and no per-item failure count.

**Why it matters.** This is precisely the "my change never reached my partner" failure mode, and it produces no error — `lastSyncError` is never set on this path. It surfaces days later as a disagreement about who was told what.

**Fix.** Replace the metadata string with a real `pending(id TEXT PRIMARY KEY, attempts INTEGER, last_error TEXT, queued_at TEXT)` table so insert/delete are atomic per row, and guard the whole read-modify-write in a `Mutex` regardless. Effort **S/M**. App-code only (local SQLite schema change → also needs **N19**).

### N3 — [P0] `save()` does not hold `syncMutex`; a concurrent `syncNow()` can delete the row that was just written

**What's wrong.** `syncNow()` acquires `syncMutex` (`HomeRepository.kt:162`) and inside it calls `database.replaceAll(merged)` (`:174`), which is `delete(items, null, null)` followed by re-insert (`LocalDatabase.kt:30-33`). `save()` never acquires that mutex. The interleaving:

1. `syncNow()` reads `val pending = pendingIds()` at `:171` — new item **X** does not exist yet.
2. `save(X)` runs `database.upsert(X)` at `:202`, then `markPending(X)` at `:203`.
3. `syncNow()` executes `database.replaceAll(merged)` at `:174`. `merged` contains neither X (not in the `pending` snapshot from step 1) nor a remote copy of X (never pushed). **X is deleted from SQLite.**
4. `pushPending()` runs at `:184` (note: *outside* the `withLock` block, which closes at `:183`). It builds `byId` from `database.readItems()` — X is absent — and hits `val local = byId[id] ?: run { clearPending(id); continue }` at `:152`, **clearing X's pending flag**.

Net result: X is present in `_items.value` (set at `:204`) so the UI looks correct, but it is absent from SQLite and from the pending set. It disappears at the next app start and never reaches the partner.

This window is opened by ordinary use, not by contention: every local write echoes back over Realtime (`SupabaseApi.kt:190`) and triggers `syncNow()` (`HomeRepository.kt:310`), and `SyncWorker` fires every 15 minutes (`HomeApplication.kt:41-47`).

**Why it matters.** It is the same class of bug the 2026-07-25 release was written to fix — "the item came back / went away after restart" — one layer below where the fix was applied. **[unverified at runtime]** — this is a read of the code, not an observed reproduction; the ordering is possible but I have not measured how often it happens.

**Fix.** Serialize all local mutations and syncs under one mutex: have `save()`/`mutate()` take `syncMutex`, or route every mutation through a single-threaded actor/`Channel`. Alternatively make `replaceAll` non-destructive (upsert remote rows + delete only ids that were in the previous remote set and are not pending). Effort **M**. App-code only.

### N4 — [P1] Local mutations are read-modify-write on `_items.value`; rapid edits lose each other on one device

**What's wrong.** `mutate()` reads a snapshot and writes back:

```kotlin
// HomeRepository.kt:313-316
private suspend fun mutate(id: String, block: (HomeItem) -> HomeItem): Result<Unit> {
    val item = _items.value.firstOrNull { it.id == id } ?: return Result.failure(NoSuchElementException(id))
    return save(block(item)).map { Unit }
}
```

and `save()` publishes with another non-atomic read-modify-write:

```kotlin
// HomeRepository.kt:204
_items.value = (_items.value.filterNot { it.id == normalized.id } + normalized)...
```

Two checklist taps in quick succession (`HomeAppRoot.kt:188`, each launching its own coroutine) both read the same pre-tap snapshot; the second write erases the first. `revision = item.revision + 1` (`:199`) is likewise computed from the stale snapshot, so both writes claim the same revision — which then collides with the server-side history trigger (see **N10**).

**Why it matters.** Ticking off a shopping list is the app's highest-frequency interaction and the one users perform fastest. "I ticked four things and one came back" is the exact complaint this produces.

**Fix.** Use `MutableStateFlow.update { }` for the publish, and apply the mutation function against the freshly-read row inside the same lock as **N3** rather than against a captured snapshot. Effort **S**. App-code only.

### N5 — [P1] The "notify the other user" switch does nothing

**What's wrong.** `QuickAddScreen.kt:118` renders `Switch(notify, …)` labelled `"הודע למשתמש השני"`; `:147` stores it as `notifyOtherUser = notify`; `JsonCodec.kt:40, 74` round-trips it. Grep over `app/src/main` finds **no read** of `notifyOtherUser` anywhere else — `deriveNotifications` (`HomeRepository.kt:73-100`) never consults it, and there is no push/FCM path at all.

**Why it matters.** In a two-person app this switch *is* the product's core promise. A user flips it, believes their partner was told, and the partner sees nothing until they happen to open the app.

**Fix.** Either wire it into `deriveNotifications` as a forced-notification flag (cheap, keeps everything local), or remove the switch until #33 lands. Do not leave it visible and inert. Effort **S**. App-code only.

### N6 — [P1] The lock-screen privacy setting does nothing

**What's wrong.** Settings exposes a switch `"תוכן במסך נעילה"` → `lockScreenContentVisible` (`DetailAndSettingsScreens.kt:404-405`), persisted at `PreferencesStore.kt:45, 62`. No other code reads it. `ReminderReceiver` builds its notification (`ReminderReceiver.kt:41-49`) with no `setVisibility(NotificationCompat.VISIBILITY_PRIVATE)` and no `setPublicVersion(...)`, and the channel is created with `IMPORTANCE_HIGH` and no lock-screen visibility (`NotificationChannels.kt`).

**Why it matters.** It is a privacy control that silently doesn't apply. The item title — which for this app may be a medical appointment or a surprise — is shown on the lock screen regardless of the setting.

**Fix.** Apply `setVisibility(if (visible) VISIBILITY_PUBLIC else VISIBILITY_PRIVATE)` in `ReminderReceiver`, with a redacted `setPublicVersion`. Effort **S**. App-code only.

### N7 — [P1] Logout leaves the previous member's preferences, read-state, PIN and alarms on the device

**What's wrong.** `logout()` (`HomeRepository.kt:289-296`) cancels realtime, clears the session, calls `database.clearAll()` and empties `_items`. But `clearAll()` is `delete("items", null, null)` only (`LocalDatabase.kt:35`) — the `metadata` table survives, carrying:

- `user_preferences` (accent, start destination, PIN timeout, default reminders, calendar layers) — `PreferencesStore.kt:76`
- `notifications_seen_at` — `PreferencesStore.kt:77`; the next member's notifications are all pre-marked read (`HomeRepository.kt:94`)
- `pending_push` — stale ids (self-healing via `:152`, but only after a sync)

Additionally `PinVault`'s SharedPreferences are untouched (`PinVault.kt:15`), so the departing member's PIN still guards the device; and `ReminderScheduler`'s `reminder_alarms` registry (`ReminderScheduler.kt:15`) is neither cleared nor are the alarms cancelled, so their reminders keep firing.

**Why it matters.** The stated model is two members with correct data separation. Handing over a phone, or re-activating in the other slot after a device swap, silently mixes their state. The notifications-seen leak is the sharpest: a member can *never see* the notifications that were generated before they activated.

**Fix.** Add `LocalDatabase.clearEverything()` that also truncates `metadata`, call `pinVault.clearPin()` and cancel all registered alarms from `logout()`. Effort **S**. App-code only.

### N8 — [P1] Exact-alarm permission is never checked; reminders silently degrade to inexact

**What's wrong.** `AndroidManifest.xml:6` declares `SCHEDULE_EXACT_ALARM`. `ReminderScheduler.setAlarm` (`:52-53`) does:

```kotlin
runCatching { alarmManager.setExactAndAllowWhileIdle(...) }
    .onFailure { alarmManager.setAndAllowWhileIdle(...) }
```

There is no `AlarmManager.canScheduleExactAlarms()` check and no `ACTION_REQUEST_SCHEDULE_EXACT_ALARM` prompt anywhere in the codebase. With `targetSdk = 37` (`build.gradle.kts:17`), `SCHEDULE_EXACT_ALARM` is a user-grantable special permission that is not guaranteed at install; when it is absent, `setExactAndAllowWhileIdle` throws `SecurityException`, the `onFailure` branch swallows it, and the alarm becomes inexact — deferrable by Doze for up to ~15 minutes or more. Nothing is logged and nothing is shown to the user.

**Why it matters.** The app's reminder promise is "tell me 30 minutes before". A silent downgrade turns that into "sometime around then", which for a doctor's appointment is the difference between useful and harmful. **[unverified at runtime]** — whether the permission is actually denied on the owners' devices is an on-device question; the missing check is a code fact.

**Fix.** Check `canScheduleExactAlarms()` at scheduling time; if false, surface a one-time settings prompt and mark affected reminders as approximate in the UI. Effort **S**. App-code only.

### N9 — [P1] Realtime has no heartbeat and no failure callbacks, and a dead socket is never replaced

**What's wrong.** `SupabaseApi.openRealtime` (`:165-194`) implements only `onOpen` (sends one `phx_join`) and `onMessage`. Missing: `onFailure`, `onClosing`, `onClosed`, any periodic `phx_heartbeat` message, and any token refresh on the live socket. `HomeRepository.ensureRealtime` (`:306-311`) short-circuits whenever `realtime != null && realtimeToken == session.accessToken`, so once the socket is dead the object is still non-null and no reconnect is attempted until `validSession()` rotates the token (`:298-304`, which only happens within 120s of expiry).

Two secondary defects in the same function: the message filter `text.contains("postgres_changes") || text.contains("INSERT") || text.contains("UPDATE")` (`:190`) matches the join **reply** (which echoes the config containing `postgres_changes`), firing a full sync on every connect; and it matches on raw text, so an item whose title contains the literal `UPDATE` would trigger syncs.

**Why it matters.** When realtime dies, the app falls back to the 15-minute `SyncWorker`. The couple experiences this as "his changes take a quarter of an hour to show up", intermittently, with no indication anything is wrong — the hardest kind of bug to report.

**Fix.** Add `onFailure`/`onClosed` that null out `realtime`/`realtimeToken` and schedule a reconnect with exponential backoff + jitter; send `phx_heartbeat` on the `phoenix` topic every ~25s; parse the message envelope for `event == "postgres_changes"` instead of substring matching; debounce `onChange` (~500ms) to coalesce bursts (this also substantially addresses **#41**). Effort **M**. App-code only.

### N10 — [P1] The server's response to a write is discarded; client-assigned revisions drift and corrupt the audit history

**What's wrong.** `SupabaseApi.upsertItem` requests `return=representation` and decodes the server row (`:143-150`), but `save()` throws it away — `:206` calls `api.upsertItem(...)` inside `runCatching{}.onSuccess{}` and then returns the locally-built `normalized` (`:210-211`). Consequences:

- The server trigger sets `new.updated_at := now()` (`0002_production_homeapp.sql:330`), so the row's `updated_at` column and the `updatedAt` **inside the payload** permanently disagree. `fetchItems` orders by the column (`SupabaseApi.kt:117`) while all app logic — notification unread state (`HomeRepository.kt:94`), sort order (`:175`), conflict tie-break (`ConflictResolver.kt:18`) — uses the payload value.
- `revision` is entirely client-assigned (`HomeRepository.kt:199`). Combined with **N4** (two writes computing the same `revision`), the history trigger's `on conflict (item_id, revision) do nothing` (`0002_…sql:328`) silently drops the second snapshot. The idempotency added in `097e0f3` correctly stopped the 409s, but it also means **revision history has silent holes**, so `homeapp_restore_item_revision` (`:339-366`) may not have the version a user wants to restore.

**Why it matters.** It is the foundation #18 has to build on: you cannot do `expected_revision` optimistic concurrency while the client owns the revision counter and ignores the server's answer.

**Fix.** Make `save()` adopt the server-returned item as the local truth on success. Move revision assignment server-side (a `BEFORE UPDATE` trigger setting `new.revision := old.revision + 1`), then have the client send `expected_revision` and treat a mismatch as a conflict. Effort **M**. **Requires a Supabase migration.**

### N11 — [P1] A permanently-failing push pins an item to its local version forever, with no cap and no signal

**What's wrong.** `syncNow()`'s merge is `remoteItems.filter { it.id !in pending } + pending.mapNotNull { localById[it] }` (`HomeRepository.kt:173`). An item in the pending set is *unconditionally excluded from remote updates*. If its push keeps failing — e.g. an `editPolicy = CREATOR_ONLY` item being edited by the non-creator, which the RLS `UPDATE` policy rejects (`0002_…sql:210-219`) — then:

- the item stays pending indefinitely (no attempt counter, no backoff, no give-up),
- every remote change to that item is discarded on every sync, forever,
- the only feedback is a transient global snackbar (`HomeAppRoot.kt:230-232`) whose text is the raw `IOException` message from `SupabaseApi.apiError` (`:237-240`).

**Why it matters.** The two devices silently and permanently diverge on that item while both show a confident UI. This is the worst kind of two-user bug: each partner is certain they're looking at the truth.

**Fix.** Add an attempt counter and a `failed`/`conflict` state per pending item (naturally alongside **N2**'s table); after N failures, stop excluding it from remote merges and surface it in the UI as needing attention. Effort **M**. App-code only.

### N14 — [P1] Tapping a reminder notification doesn't open the item

### N18 — [P2] Undecodable items vanish silently from both the cloud fetch and the local cache

**What's wrong.** `SupabaseApi.fetchItems` uses `mapNotNull { runCatching { JsonCodec.decode(...) }.getOrNull() }` (`:121-126`) and `LocalDatabase.readItems` uses `runCatching { JsonCodec.decode(...) }.getOrNull()` (`:18`). `JsonCodec.decode` hard-requires `id`, `type`, `title`, `creatorId`, `createdAt`, `updatedAt` and `Instant.parse`s several fields (`JsonCodec.kt:44-76`), so any payload written by a future app version with a changed shape decodes to `null`, is dropped from the list, and is then persisted away by `replaceAll` (`HomeRepository.kt:174`). No error, no count, no log.

**Why it matters.** A forward-compatibility mistake in a future release becomes silent data loss on the older device rather than a visible failure. (Restated from **#21** because the evidence is worth having in one place.)

**Fix.** Count decode failures; if any occur, fail the sync rather than committing a partial snapshot, and surface the count. Effort **S**. App-code only.

### N19 — [P2] `LocalDatabase.onUpgrade` is a no-op

**What's wrong.** `LocalDatabase.kt:15` — `override fun onUpgrade(db, oldVersion, newVersion) = Unit`, with `version = 1` (`:9`). Any future bump silently skips migration and leaves the old schema, producing `SQLiteException` at query time.

**Fix.** Implement a real upgrade path (or, given the DB is a pure cache, `DROP` + recreate + force a full resync, which is legitimate here and much simpler). Effort **S**. App-code only.

### N21 — [P2] Natural-language parser: unanchored Hebrew weekday matching, and "Monday" never means today

**What's wrong.** `NaturalLanguageParser.parseWeekday` (`:56-68`) does `names.entries.firstOrNull { it.key in text }` — an unanchored substring test. `"שני"` is a substring of `"שניים"`, `"שנייה"`, `"משני"`; `"שבת"` of `"שבתאי"`. ## 5. Leave this alone / not worth it

**#23 — unifying the cloud data model (normalize comments/receipts/notifications out of the payload).**
Genuinely diagnosed, correctly reasoned, and still the wrong thing to do here. Normalizing means a large migration, a rewrite of `JsonCodec`, `SupabaseApi` and `HomeRepository`, plus a data backfill — all to reduce write amplification for a dataset of two people and a few hundred items. The actual harm it causes (whole-aggregate writes enabling lost updates) is addressed far more cheaply by **N10 + #18** (server-owned revision + `expected_revision`) and by `ConflictResolver`-style field merging. **Recommendation: close #23 as WONTFIX with a note pointing at #18.** Revisit only if #44 (multi-household) is ever actually started.

**#44 — multi-household / distribution readiness.**
Correctly scoped by its author as far-future and correctly ordered last. Nothing in it benefits the two people using the app today, and several items (generic branding, tenancy isolation, invitation flows, provisioning UI) are more work than the entire current app. **Recommendation: leave open as a design note; do not schedule.** The one sub-item worth doing *early* if the repo's visibility ever changes is the secret-history audit — but the repo is private and the code hashes were already sentinelized (`0002_…sql:416-417, 423-424`).

**#41 — incremental Realtime processing.**
The diagnosis is right (every event triggers a full refetch) but the remedy is oversized. At two users and a few hundred items, a full sync is a couple of small HTTP requests. A **500 ms debounce on `onChange`** (part of 2.5) removes the burst amplification for ~5 lines, whereas parsing `postgres_changes` payloads and maintaining an incremental projection adds a whole new consistency surface — one that is much harder to get right than the full refetch it replaces. **Recommendation: implement the debounce, then close #41.**

**#37 — full he/en localization.**
Extracting ~300 hardcoded Hebrew strings into resources and translating them is a multi-day job whose beneficiary is a hypothetical English-speaking user of a two-person Hebrew household app. **Recommendation: delete the language setting (`DetailAndSettingsScreens.kt:398, 449-450`) and the `en` entry in `locales_config.xml`, keep the RTL fix that already landed, and close #37 as "Hebrew-only by design."** The three things worth keeping from that issue are already cheap and listed separately: the English strings in `ReminderReceiver` (**should be translated to Hebrew**, not extracted), and the auto-mirrored icons (**N12**).

**#39 — recurrence — unless it is actually wanted.**
`RecurrenceEngine` is 43 lines of correct, tested, entirely unused code. Wiring it up properly is genuinely large: recurrence UI, occurrence expansion in four views, this-vs-following-vs-series edit semantics, DST handling, per-occurrence reminders, and a cloud representation. **Recommendation: ask whether a recurring item has ever actually been wanted. If not, delete `RecurrenceEngine.kt`, `RecurrenceEngineTest.kt` and `RecurrenceRule` and close #39.** Half-built features are a permanent tax on every future reader.

**`ConflictResolver` as-is.**
The three-way merge is well-written but needs a *base* version to merge against, and nothing in the app stores base snapshots — which is why it was never wired up. Do not force it into the save path to satisfy #18's checklist. `expected_revision` + refetch + a field-level merge on demand is simpler and matches how the data actually behaves. **Recommendation: keep the file only if #18 is scheduled; otherwise delete it with the rest of N24.**

**Full accessibility conformance.**
45 null content descriptions is a real number, but the app has two known users and no known assistive-technology requirement. Doing the ~10 icon-only *actions* (**4.9**) captures nearly all the practical value; a full WCAG pass, touch-target audit and colour-contrast review does not. **Recommendation: do 4.9, skip the rest.**

**Migrating off raw SQLite / org.json to Room + kotlinx.serialization.**
Tempting, and genuinely better practice. But `LocalDatabase` is 51 lines and `JsonCodec` is 87, both are readable, and neither is the source of any finding in this document — the bugs are in *concurrency around* them, which Room would not fix. Adding two dependencies and a KSP processor to a project whose entire build is currently 91 lines is a bad trade. **Recommendation: no.**

**Supabase side** (`supabase/migrations/0002_production_homeapp.sql`, 442 lines; `0001` was removed in `2ea0b19`):

- **Live tables:** `homeapp_households`, `homeapp_profiles`, `homeapp_items` (the aggregate), `homeapp_item_revisions` (written only by the trigger), `homeapp_activation_slots`, `homeapp_devices`, `homeapp_device_requests`, `homeapp_activation_attempts`.
- **Defined but unused by the app:** `homeapp_comments`, `homeapp_read_receipts`, `homeapp_item_links`, `homeapp_notifications`, `homeapp_user_preferences`, `homeapp_backup_snapshots` — all with full RLS and grants (see #23).
- **RLS model:** everything keys off `auth.jwt() -> app_metadata -> household_id`, which only the Edge Function's service key can set (`activation/index.ts:117, 135`). Notable policies: `homeapp_items_select` (`:193-203`) hides another member's unpublished `NOTE`; `homeapp_items_update` (`:210-219`) enforces `edit_policy`; `homeapp_items_no_delete` (`:221-222`) forbids hard deletes, which is why delete is soft.
- **Trigger:** `capture_item_revision()` (`:315-333`) is `SECURITY INVOKER`, snapshots the pre-image into `homeapp_item_revisions` with `on conflict do nothing`, and forces `new.updated_at := now()`.
- **Edge Functions:** `activation` (device activation / status / approve, rate-limited, service-role) and `fridge-display-api` (read-only household agenda for a kitchen display, guarded by `FRIDGE_DISPLAY_KEYS`, defaults to `Asia/Jerusalem`).

**Key architectural properties.** No ViewModels — Compose observes repository flows directly, so all screen state that isn't `remember`ed is lost on process death. No DI framework. No Room/Retrofit/serialization library — hand-rolled `org.json` + OkHttp throughout. The `HomeItem` aggregate is the single unit of transfer, storage and conflict.

## Appendix B — End-to-end data flow of a single item write

Traced for: *user edits an item's title in the detail screen and taps שמירה*. Past bugs clustered here, so every step is cited.

### B.1 The happy path

| Step | Where | What happens |
|---|---|---|
| 1 | `DetailAndSettingsScreens.kt:119-126` | Button builds `item.copy(title=…, body=…, assignee=…, pinned=…, startAt/dueAt=…)` from local `remember(item.id)` state (`:57-61`) and calls `onSave(...)`, then sets `editing = false` **unconditionally** — the UI leaves edit mode before any result is known. |
| 2 | `HomeAppRoot.kt:183` | `scope.launch { repository.save(changed).onSuccess { reminderScheduler.schedule(it, user.id); selectedItem = it } }`. Note the screen's snapshot `selectedItem` only advances on success. |
| 3 | `HomeRepository.kt:192-201` | `save()` on `Dispatchers.IO`. Normalizes: `householdId` from session, `creatorId` from session unless already a real id (the `u1`/`u2` guard at `:197`), **`revision = item.revision + 1` (client-assigned — N10)**, `updatedAt = Instant.now()`. |
| 4 | `HomeRepository.kt:202` | `database.upsert(normalized)` → `insertWithOnConflict(CONFLICT_REPLACE)` with `payload = JsonCodec.encode(item)` (`LocalDatabase.kt:21-26`). **Durable from here.** |
| 5 | `HomeRepository.kt:203` | `markPending(id)` → read-modify-write of `metadata["pending_push"]` (**N2 race**). |
| 6 | `HomeRepository.kt:204` | `_items.value = (filterNot{id} + normalized).filter{ status != CANCELLED }.sortedBy{updatedAt}` (**N4 race**). UI updates instantly. |
| 7 | `HomeRepository.kt:205-206` | If `api.configured && session != null`: `validSession()` (`:298-304`) refreshes the token if it expires within 120 s, then `api.upsertItem(normalized, session)`. |
| 8 | `SupabaseApi.kt:130-145` | Builds the row: scalar columns (`id`, `household_id`, `creator_id`, `type`, `status`, `edit_policy`, `revision`, `created_at`, `updated_at`) **plus the whole item again** as `payload` (`JsonCodec.encode`). `POST /rest/v1/homeapp_items?on_conflict=id`, `Prefer: resolution=merge-duplicates,return=representation`. **No `expected_revision` (#18).** |
| 9 | Postgres | `INSERT … ON CONFLICT (id) DO UPDATE`. RLS `homeapp_items_update` checks household + `edit_policy` (`0002_…sql:210-219`). `BEFORE UPDATE` trigger `capture_item_revision` (`:315-333`) writes the **pre-image** to `homeapp_item_revisions` (skipping on `(item_id, revision)` conflict — **N10 history hole**) and sets `new.updated_at := now()`, diverging the column from the payload's `updatedAt`. |
| 10 | `SupabaseApi.kt:146-150` | Decodes the returned representation… |
| 11 | `HomeRepository.kt:206-211` | …and **discards it** — `onSuccess { clearPending(id); lastSyncError = null }`, then `val saved = normalized; saved`. The local copy, not the server's, becomes the result (**N10**). |
| 12 | Postgres → WAL | The row change is published to `supabase_realtime` (`0002_…sql:430-432`). |
| 13 | `SupabaseApi.kt:189-191` | **The writer's own device** receives the echo; the substring filter matches `UPDATE`, so `onChange()` fires. |
| 14 | `HomeRepository.kt:310` | `scope.launch { syncNow() }` → a **full** refetch of all profiles + all items, on the device that just wrote (**#41 / N9**). |
| 15 | Partner's device | Same echo → `syncNow()` → `fetchItems` (`SupabaseApi.kt:115-127`, unpaginated, silently dropping undecodable rows — **N18**) → merge (`HomeRepository.kt:171-173`) → `database.replaceAll(merged)` (`:174`) → `_items` updated → recomposition. |
| 16 | `HomeAppRoot.kt:183` | Back on the writer: `onSuccess` schedules alarms for the *current user's* reminders (`ReminderScheduler.kt:19-33`) and advances `selectedItem`. |

### B.2 Where it goes wrong

- **Offline (steps 7-11 skipped).** `save()` still completes: SQLite has it, the item stays pending, `lastSyncError` shows a snackbar. Correct behaviour — but **N1** means the user could not have reached step 1 from the Add sheet at all, and could not have pinned/archived/completed from the detail screen.
- **Concurrent `syncNow()` between steps 4 and 5 (N3).** `replaceAll` at `:174` deletes the row written in step 4; `pushPending` at `:152` then clears the pending flag set in step 5. The item survives only in `_items` (step 6) and is gone at next launch.
- **Two writes racing (N4).** Both read the same base at `mutate` (`:313-316`); the second overwrites the first, and both stamp the same `revision`, so step 9's history insert silently no-ops for one of them.
- **Push fails permanently (N11).** The item stays in `pending` forever; step 15's merge (`:173`) excludes it from remote updates on every subsequent sync, so the two devices diverge silently and indefinitely.
- **Step 1 lies.** `editing = false` runs before the result is known; a failure surfaces only as a global snackbar (`HomeAppRoot.kt:230-232`) carrying a raw `IOException` string (`SupabaseApi.kt:237-240`).
- **Comments and checklist take the same path.** `onSave(item.copy(comments = item.comments + Comment(...)))` (`DetailAndSettingsScreens.kt:210`) and `toggleChecklist` (`HomeRepository.kt:219-225`) both rewrite the **entire aggregate**, so a comment posted on one device and a checklist tick on the other are a genuine lost-update pair — the mechanism behind **#18** and **#23**.
